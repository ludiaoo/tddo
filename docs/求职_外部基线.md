# 外部基线：OR-Tools 纯卡车 VRPTW 对照

> 用途：回答面试必问的「和 OR-Tools / 开源求解器比怎么样」。这是求职评估里的 P0 补齐项。
> 复现命令：`python -m scripts.ortools_baseline`（需 `requirements-dev.txt` 中的 OR-Tools）。
> 原始结果：`results/ortools_baseline.csv`，表格：`results/ortools_baseline.md`。

## 1. 一句话结论

在**卡车侧子问题**上，OR-Tools 与自写 ALNS 在 6/8 个算例上几乎同成本（差 ≤0.01%）；
西雅图 100 客户 OR-Tools 略优 0.21%，天河 100 客户我们的 ALNS 用约 1/3 的墙钟便宜 **4.5%**。
但这只对比了纯卡车 VRPTW，**不能说「我们比 OR-Tools 强」**——原问题里的无人机同步、换电、
单架次电量与时空禁飞区，OR-Tools 的路由模型无法直接表达。

## 2. 对照模型怎么建的

| 项目 | 处理 |
|---|---|
| 求解器 | OR-Tools `RoutingModel` 9.15，`PATH_CHEAPEST_ARC` 初始解 + `GUIDED_LOCAL_SEARCH`，单线程限时 |
| 节点 / 时间窗 / 路网 | 与 `Instance` 完全一致：同一批 set、同一组 `(e_i, l_i)`、同一张有向卡车距离/时间矩阵 |
| 车数 / 服务时间 / 容量 | 与 `Instance` 一致；容量按派件量 `f_i` 约束 |
| 成本口径 | 与评估器一致：燃油 `0.35 L/km × 1.30 $/L` + 司机工时 `0.0063 $/s × 返仓时刻`；司机成本用时间维度 span cost 计入，**包含时间窗等待** |
| **放松项** | 不计取件载荷 `g_i`；不派无人机，因此禁飞区 / 电量 / 换电都不出现 |
| 自检 | OR-Tools 目标值 ÷ 1e6 与用项目评估器公式重算的成本，在 8/8 个算例上差值 **0.0000** |

时间维度把「服务时间」加在**出发节点**的 transit 上，因此客户节点的 CumulVar 是到达时刻
（可套时间窗），末端 CumulVar 是返仓时刻；等待通过 `slack_max` 放开。这一处如果写错，
时间窗几乎必然报不可行——烟雾测试时确实踩过并修掉了。

## 4. 怎么解读（面试话术）

1. **先讲可比的部分**：「我在同一批算例上用 OR-Tools 建了纯卡车 VRPTW，节点、时间窗、
   路网矩阵、车数和成本系数都跟我的评估器一致，目标值逐位对得上。10/25/50 客户上它和我的
   ALNS 卡车侧几乎一样，说明我的卡车侧实现没有偷偷放松约束。」
2. **再讲差异**：「100 客户天河算例上，OR-Tools 给 371.49 用了 40 s，我的 ALNS 给 355.50
   用了约 27 s，便宜 4.5%。但它是限时搜索，不是证明最优；而且我这边取件载荷也没进它的容量，
   所以我不会把这说成『全面超过 OR-Tools』。」
3. **最后划清问题边界**：「原问题有无人机同步、换电、电量和禁飞区，OR-Tools 路由模型表达不了，
   所以我只对比卡车侧子问题。全模型相对纯卡车的节省是另一条轴：天河 100 客户上是 10.7%，
   西雅图上是 16%–29%，这和换电机制的 1.5%–3.4% 不是同一个数。」

## 5. 明确不能说的话

- 不能说「我们的 ALNS 比 OR-Tools 好」——只比了一个松弛子问题，且两边都是启发式/限时搜索。
- 不能把 16%–29% 当成「算法精度」——那是卡车 + 无人机相对纯卡车方案的成本降幅。
- 不能把 OR-Tools 的数当原问题下界——取件载荷被放松，而且没有最优性证书。
- 不能混用天河与西雅图的数字——两套底图不可横比。
